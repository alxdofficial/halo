# Episodic training profile: where the time actually goes

**Date** 2026-08-19 · RTX 4090 (24 GiB) · `--profile` / `--profile-trace` on
`training/tokenizer/pretrain_episodic.py` · real corpus, 4 episodes/step, 12 timed steps after
4 warmup.

## Headline

The pipeline is **CPU-dispatch-bound, not compute-bound and not data-bound.**

| | Self CPU | Self CUDA | ratio | device utilisation |
|---|---:|---:|---:|---:|
| encoder only (`--no-mixer`) | 36.4 ms | 7.9 ms | **4.6x** | 53% |
| encoder + mixer (default) | 62.7 ms | 15.8 ms | **4.0x** | 68% |

Peak GPU memory is **0.44 of 24 GiB — 1.8% of the card.**

## Phase split

| phase | ms/step | share |
|---|---:|---:|
| forward | 36.0 | 59.1% |
| backward | 23.7 | 38.9% |
| optimizer + clip | 1.0 | 1.6% |
| **data (loader wait)** | **0.3** | **0.4%** |

The loader is not the bottleneck and never waits. This corrects an assumption carried from an
earlier session, where a 48% `nvidia-smi` reading was read as data starvation; it is dispatch
overhead instead.

## What each part costs

| config | forward | backward | wall/step | GPU mem |
|---|---:|---:|---:|---:|
| no mixer | 35.0 | 8.3 | 45.2 | 0.30 GiB |
| mixer, pool 64 | 38.7 | 24.2 | 65.0 | 0.41 GiB |
| mixer, pool 256 | 38.4 | 23.8 | 64.4 | 0.44 GiB |

- **Mixer: ~4.75 ms/episode**, and an isolated microbenchmark at the real episode shapes gives
  4.95 ms — the two agree, so the attribution is sound.
- **Pool 64 and pool 256 cost the same.** Attention over 458 vs 1034 tokens is indistinguishable,
  so the cost is size-independent dispatch, not FLOPs. Capping the pool buys no speed; keeping it
  at 256 is free.
- **The encoder is the larger target**: forward 8.75 ms/episode against backward 2.1 ms, a 4.2:1
  ratio. A differentiable forward should be roughly 1:2. Four-to-one means most of that forward is
  CPU work with no backward at all.

## Two levers that do NOT work — measured, not assumed

| | mixer fwd+bwd |
|---|---:|
| eager | 4.95 ms |
| `torch.compile(dynamic=True)` | 5.01 ms — **no gain** |
| bf16 autocast | 5.65 ms — **14% worse** |

Autocast loses because the modules are small enough that the cast overhead exceeds the arithmetic
saving. Compile cannot fuse much with dynamic shapes, which episodes require.

## The actual inefficiency

`model/tokenizer/encoder.py`, on the hot path, per forward:

1. **The frozen text encoder re-runs on the same strings every episode.**
   `encode_texts_unique` de-duplicates within a batch and then calls
   `self.text_encoder.encode(unique)`. The sensor and role descriptions come from a small closed
   vocabulary and the LM is frozen, so this is the same computation repeated ~12,000 times over a
   3k-step run. A text -> (embedding, mask) cache keyed on the string removes it entirely.

2. **One tensor construction and host-to-device copy per batch row.**
   `encode_texts_factored_unique` builds `sensor_text_ids` inside a Python loop, calling
   `torch.tensor(..., device=device)` once per window — about 144 tiny transfers per episode. This
   is visible in the trace as 408 `aten::copy_` calls. Building the whole table on CPU and issuing
   a single `.to(device)` collapses it to one.

Neither changes any number the model produces; both are pure dispatch reduction on the phase that
is 59% of the step and 4.2:1 forward-heavy.

## Secondary headroom

- **Memory is 55x under-used.** Episodes are processed sequentially in a Python loop
  (`for _ in range(episodes_per_step)`), so raising `--episodes-per-step` adds sequential work
  rather than parallel work and will not help. Batching several episodes into ONE heterogeneous
  forward would — the encoder already accepts heterogeneous batches, which is what makes an episode
  one forward instead of twenty. That is a real code change, not a flag.
- **Validation is not free**: 96 episodes at every checkpoint. At 13 checkpoints that is ~1,250
  episodes against 12,000 training episodes, roughly 10% of the run.

## Reproducing

```
python -m training.tokenizer.pretrain_episodic --checkpoint <phase-A> --profile 12 --profile-trace
```

Phase boundaries synchronise, which is the only way to attribute wall time on an async device and
which also serialises the pipeline. Read the shares, not the absolute step time.
